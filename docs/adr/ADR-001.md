# ADR-001: Capas simples para persistencia; el seam de notificacion ya cubre el proximo cambio conocido

## Estado: Aceptado — 2026-10-31

## Contexto
Tras integrar Chain of Responsibility, Strategy y Observer sobre el sistema de solicitudes de reembolso, corresponde decidir si el proyecto debe migrar a arquitectura Hexagonal completa (puertos e interfaces intermedias para persistencia y notificacion) o mantenerse en capas simples. No existe hoy ningun plan de cambiar el motor de base de datos relacional. Contabilidad si anuncio, para el proximo trimestre, una integracion por API externa para el pago de solicitudes aprobadas.

## Decision
Se mantiene arquitectura en capas simples para la persistencia: `SolicitudReembolsoService` sigue dependiendo directamente de `RepositorioSolicitudesJpa`, sin una interfaz de puerto intermedia (`RepositorioSolicitudes`) ni un adaptador de traduccion de entidades. Un puerto de persistencia hoy seria una abstraccion especulativa (violando YAGNI) sin ningun driver de cambio real que lo requiera.

Para la notificacion no se introduce ningun puerto adicional: la interfaz `ObservadorCambioEstado` del patron Observer ya actua como el *seam* (punto de costura arquitectonico) necesario, y `NotificadorContabilidad` puede reemplazar su implementacion interna (`System.out.println`) por un cliente HTTP hacia la API externa de pagos el proximo trimestre sin modificar `SolicitudReembolsoService` ni los demas observadores.

## Consecuencias

### Positivas:
- No se agregan interfaces redundantes, adaptadores ni mappers de persistencia sin un caso de uso real que los justifique (cumplimiento de YAGNI y KISS).
- El unico cambio de infraestructura con fecha cierta y conocida (integracion con API externa de Contabilidad el proximo trimestre) ya cuenta con su punto de extension desacoplado a traves de `ObservadorCambioEstado`.
- Menor sobrecarga cognitiva y menor cantidad de archivos boilerplate que mantener en el repositorio.

### Negativas:
- Si en el futuro surge la necesidad real de cambiar a un motor de persistencia no soportado por Spring Data JPA, el puerto de salida `RepositorioSolicitudes` debera extraerse mediante refactoring retroactivo; se acepta esa deuda tecnica potencial de forma consciente.
- Un revisor externo que espere simetria arquitectonica estricta (puertos explicitos en todas las dependencias de salida) puede percibir la convivencia de `RepositorioSolicitudesJpa` directo y `ObservadorCambioEstado` como asimetrica si no consulta este ADR.
